# 1CXML — инструментарий описания и выгрузки метаданных любой конфигурации 1С

Набор инструментов, который превращает структуру метаданных **любой** конфигурации
1С:Предприятие в редактируемое машиночитаемое описание и позволяет по этому
описанию выгружать данные. Главная цель — дать нейросетям (вайб-кодинг) точную,
управляемую карту полей и типов конфигурации, а также управляемый механизм
выгрузки данных любого объёма.

## Состав

```
1c/                       Обработки 1С (исходники модулей на BSL)
  src/
    ВыгрузкаСтруктурыМетаданных.bsl   ① выгрузка структуры → .1cmeta (NDJSON)
    ВыгрузкаДанныхПоСхеме.bsl         ③ выгрузка данных по схеме → .1cdata (NDJSON)
  README.md               Как собрать внешние обработки из исходников
docs/
  FORMAT.md               Спецификация форматов .1cmeta и .1cdata
editor/                   ② GUI-редактор схемы (Python + PySide6)
  src/onec_schema_editor/
  tests/
examples/
  sample.1cmeta           Демо-схема для проверки редактора без 1С
```

## Конвейер

```

│ ① Выгрузка структуры     │ ───────────► │ ② GUI-редактор схемы  │ ───────────► │ ③ Выгрузка данных по    │

└─────────────────────────┘              └──────────────────────┘              └────────────────────────┘
        любая КФ                          галки/типы/поиск/замена/                  .1cdata (один файл,
                                          высушивание/статистика                    по объектам, многотомно)
```

## Почему NDJSON

Файлы описаний типовых конфигураций — это сотни тысяч узлов, а данные — гигабайты.
**NDJSON** (одна строка = один JSON-объект) даёт:

* потоковую запись/чтение и в 1С, и в Python — без удержания всего файла в памяти;
* дешёвое разбиение на тома и склейку (`cat`), быстрый `grep`;
* устойчивость: битая строка не рушит весь файл.

Подробности — в [docs/FORMAT.md](docs/FORMAT.md).

## Быстрый старт

### ② Редактор (можно проверить прямо сейчас, без 1С)

```bash
cd editor
python -m pip install -r requirements.txt
python -m onec_schema_editor ../examples/sample.1cmeta
```

Тесты логики (без GUI):

```bash
python -m pytest editor/tests -q
```

### ① и ③ Обработки 1С

Исходники модулей лежат в `1c/src/*.bsl`. Как обернуть их во внешние обработки
(`.epf`) и запустить интерактивно или программно — см. [1c/README.md](1c/README.md).

## Возможности GUI-редактора

* Дерево всей конфигурации с цветовой индикацией видов и **tri-state чекбоксами**
  (включение/исключение узлов в выгрузку с каскадом на поддерево).
* Колонки: Имя / Вид / Тип / Синоним / Полное имя; тип отображается человекочитаемо
  (`Строка(25)`, `Число(15,2)`, `→ Справочник.Номенклатура`, `Составной: …`).
* **Поиск и замена** по имени / синониму / типу / полному имени / везде, с
  регистром и regex; «отметить/снять найденные»; массовая замена (в т.ч. в `meta`
  ссылочных типов — удобно при переносе схемы между конфигурациями).
* **Высушивание составных типов**: оставить подмножество типов либо разнести по
  отдельным узлам (split) с суффиксами.
* **Редактор типа**: смена примитива/ссылки, квалификаторы (длина, разрядность, …).
* Смена вида узла, удаление узла/поддерева.
* **Статистика**: всего узлов, отмечено, объектов с данными, составных типов,
  гистограмма по видам, уникальные ссылочные цели.
* Массовые операции: отметить всё / снять всё / только узлы с данными.

## Возможности выгрузки данных (③)

* Параметры отбора: `ДатаНачала`, `ДатаОкончания`, `Организация`, `Подразделение`
  (применяются, только если поле реально есть у объекта).
* Режимы разбиения файлов: `single` | `objects` (файл на объект) |
  `volumes` (многотомно) | `objects+volumes`.
* **Чанкинг серверных вызовов**: каждая порция — отдельный запрос
  `ВЫБРАТЬ ПЕРВЫЕ N … ГДЕ Ссылка > &Курсор` (keyset-пагинация), что не даёт
  одному вызову превысить лимиты памяти `rphost`. Табличные части читаются
  батчами по ссылкам уже выбранной порции. Регистры чанкуются окнами периода.
* Запуск интерактивно (с формы) и программно (`ВыгрузитьДанные(...)`).

## Реализовано в редакторе (помимо базового)

* **Импорт из Configuration.xml / EDT** — построение `.1cmeta` без запуска 1С.
* **Профили выгрузки** — именованные пресеты галок и настроек.
* **Diff двух схем** между релизами/конфигурациями.
* **Валидатор ссылочной целостности** `meta`.
* **Паспорт для LLM** — компактный Markdown/JSON-срез только отмеченного.
* **Просмотрщик `.1cdata`** и **граф связей** объектов.
* **Оценка объёмов** по схеме и факту выгрузки.

## СУБД и Yandex Cloud (вкладка «Интеграции»)

* Генерация `schema.sql` (DDL) по дереву для **MariaDB**, **YC Managed ClickHouse**,
  **YC Managed YDB**. Имена транслитерируются (переключаемо), ссылки кладутся как
  `id` + `_view` (представление).
* Загрузка выгруженных `.1cdata` в созданные таблицы с **прогресс-баром в отдельном
  потоке** (видно, что процесс жив).
* **Архивирование** выгрузки (tar.gz) и отправка в **YC Object Storage (S3)**.
* Параметры подключения для каждой СУБД/хранилища — в своих вкладках.

Драйверы (`PyMySQL`, `clickhouse-connect`, `ydb`, `boto3`) опциональны —
см. `editor/requirements-integrations.txt`.

## Что ещё стоит прикрутить из Яндекс-Облака (предложения)

* **YC Lockbox** — хранить пароли/ключи СУБД и S3 в секрет-менеджере, а не в полях.
* **YC Data Transfer** — поставить нашу выгрузку источником/приёмником для
  непрерывной репликации в ClickHouse/YDB.
* **YC DataLens** — автогенерация датасета/дашборда поверх залитых таблиц.
* **YC Managed PostgreSQL / Greenplum** — ещё один бэкенд DDL+загрузки.
* **YC Message Queue (SQS-совместимая) / Yandex Data Streams** — потоковая отправка
  строк `row` вместо батч-загрузки (для near-real-time).
* **YC Functions / Serverless Containers** — запуск загрузчика по триггеру на
  появление архива в Object Storage.
* **YC IAM (сервисные аккаунты, метаданные ВМ)** — авторизация без ключей в файлах
  (для YDB уже поддержано `use_metadata_creds`).
* **YC Object Storage lifecycle + Cold storage** — автоархивация старых выгрузок.
* **YC Monitoring** — слать метрики прогресса/ошибок загрузки.
