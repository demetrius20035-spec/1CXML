# Формат `.1cmeta` — описание структуры метаданных 1С (NDJSON)

Файл `.1cmeta` — это **NDJSON** (Newline Delimited JSON): каждая строка файла —
самостоятельный JSON-объект в кодировке UTF-8 (без BOM), строки разделяются `\n`.

Такой формат выбран потому, что:

* **Потоковая запись/чтение.** И 1С (`ЗаписьТекста`/`ЧтениеТекста`), и Python
  читают/пишут файл построчно, не держа его целиком в памяти. Это критично:
  выгрузка метаданных крупной типовой (ERP, КА, УХ) — это сотни тысяч узлов.
* **Дописывание и склейка.** Тома можно склеивать простым `cat`, искать — `grep`.
* **Дешёвое разбиение на тома** (см. обработку выгрузки данных).

> Файлы данных (результат второй обработки) используют тот же контейнерный
> формат NDJSON, но с другими типами записей — см. раздел «Формат файла данных».

---

## 1. Общая структура файла схемы

```
{"$":"header", ...}            ← ровно одна строка, всегда первая
{"$":"node", "id":1, ...}      ← узлы дерева, в порядке обхода (родитель раньше детей)
{"$":"node", "id":2, ...}
...
{"$":"footer", "nodes":12345}  ← необязательная последняя строка с контрольной суммой
```

Поле `$` (dollar) — **дискриминатор типа записи**. Возможные значения: `header`,
`node`, `footer`. Неизвестные значения `$` парсеры обязаны пропускать (forward-compat).

---

## 2. Запись `header`

| Поле            | Тип     | Описание                                                        |
|-----------------|---------|-----------------------------------------------------------------|
| `$`             | string  | `"header"`                                                      |
| `format`        | string  | Всегда `"1cmeta-ndjson"`                                        |
| `version`       | number  | Версия формата. Текущая — `1`                                   |
| `config`        | string  | Имя конфигурации (`Метаданные.Имя`)                            |
| `configSynonym` | string  | Синоним конфигурации                                            |
| `configVersion` | string  | Версия конфигурации (`Метаданные.Версия`)                      |
| `platform`      | string  | Версия платформы (`СистемнаяИнформация.ВерсияПриложения`)      |
| `generated`     | string  | Дата-время выгрузки в ISO 8601                                  |
| `vendor`        | string  | Поставщик (`Метаданные.Поставщик`)                             |

---

## 3. Запись `node`

Узел дерева метаданных. Дерево восстанавливается по паре `id`/`parent`.
Корень имеет `parent: 0`.

| Поле        | Тип       | Обяз. | Описание                                                              |
|-------------|-----------|-------|-----------------------------------------------------------------------|
| `$`         | string    | да    | `"node"`                                                              |
| `id`        | number    | да    | Уникальный целочисленный идентификатор узла в пределах файла          |
| `parent`    | number    | да    | `id` родителя; `0` для корня                                          |
| `kind`      | string    | да    | Вид узла (см. §4)                                                     |
| `name`      | string    | да    | Имя (как в конфигураторе)                                            |
| `synonym`   | string    | нет   | Синоним                                                              |
| `fullName`  | string    | нет   | Полное имя объекта (`Справочник.Номенклатура`)                       |
| `comment`   | string    | нет   | Комментарий из конфигуратора                                         |
| `sel`       | boolean   | да    | **Чекбокс**: включён ли узел в схему выгрузки данных. По умолчанию `true` |
| `types`     | array     | нет   | Описание типа (см. §5). Присутствует у узлов-полей                   |
| `composite` | boolean   | нет   | `true`, если тип составной (в `types` > 1 элемента)                  |
| `props`     | object    | нет   | Вид-специфичные свойства (см. §4)                                    |

### Поле `meta` (служебное, добавляется редактором)

Редактор может добавлять к узлу объект `meta` с пользовательскими пометками
(`note`, `tag`, `color` и т.п.). 1С-обработки эти поля игнорируют.

## 4. Значения `kind`

### Структурные (без данных, для навигации)

| kind             | Описание                                                  |
|------------------|-----------------------------------------------------------|
| `ConfigRoot`     | Корень конфигурации                                       |
| `MetadataClass`  | Класс объектов: «Справочники», «Документы», «РегистрыСведений» … |

### Прикладные объекты (носители данных)

| kind                      | 1С-класс                       |
|---------------------------|--------------------------------|
| `Constant`                | Константа                      |
| `Catalog`                 | Справочник                     |
| `Document`                | Документ                       |
| `DocumentJournal`         | ЖурналДокументов               |
| `Enum`                    | Перечисление                   |
| `ChartOfCharacteristicTypes` | ПланВидовХарактеристик      |
| `ChartOfAccounts`         | ПланСчетов                     |
| `ChartOfCalculationTypes` | ПланВидовРасчета               |
| `InformationRegister`     | РегистрСведений                |
| `AccumulationRegister`    | РегистрНакопления              |
| `AccountingRegister`      | РегистрБухгалтерии             |
| `CalculationRegister`     | РегистрРасчета                 |
| `BusinessProcess`         | БизнесПроцесс                  |
| `Task`                    | Задача                         |
| `ExchangePlan`            | ПланОбмена                     |
| `Report`                  | Отчёт (без данных, но в схеме) |
| `DataProcessor`           | Обработка                      |

### Поля и подчинённые коллекции

| kind                  | Описание                                                       |
|-----------------------|----------------------------------------------------------------|
| `StandardAttribute`   | Стандартный реквизит (Ссылка, Код, Наименование, Дата, Номер, Проведён, ПометкаУдаления …) |
| `Attribute`           | Реквизит                                                      |
| `TabularSection`      | Табличная часть (контейнер; данные — в её `Attribute`)        |
| `StandardTabularSection` | Стандартная табличная часть                                |
| `Dimension`           | Измерение регистра                                            |
| `Resource`            | Ресурс регистра                                               |
| `EnumValue`           | Значение перечисления                                         |
| `AccountingFlag`      | Признак учёта (План счетов)                                   |
| `ExtDimensionAccountingFlag` | Признак учёта субконто                                  |
| `Recalculation`       | Перерасчёт (Регистр расчёта)                                  |
| `Command`             | Команда (для полноты структуры)                               |

`props` для отдельных видов:

* `Document.props.registerRecords` — массив полных имён регистров-движений.
* `InformationRegister.props.periodicity` — периодичность (`НеПериодический`,
  `ВПределахСекунды`, `ВПределахДня`, …); `props.writeMode` — режим записи.
* `AccumulationRegister.props.registerType` — `Остатки` / `Обороты`.
* `Enum` — дети `EnumValue` не имеют `types`.
* `Catalog.props.hierarchical` — иерархический ли; `props.hierarchyType`.

## 5. Описание типа — массив `types`

`types` — массив дескрипторов. Если элементов > 1 → тип составной (`composite: true`).
Каждый дескриптор — объект с дискриминатором `t`:

### Примитивные

```jsonc
{"t":"String",  "len":25, "allowedLength":"Variable"}   // или "Fixed"
{"t":"Number",  "digits":15, "fraction":2, "nonNegative":false}
{"t":"Date",    "dateParts":"DateTime"}                 // Date | Time | DateTime
{"t":"Boolean"}
{"t":"UUID"}
{"t":"ValueStorage"}
{"t":"Null"}
{"t":"Type"}                                            // Тип
```

### Ссылочные

```jsonc
{"t":"Ref", "meta":"Справочник.Номенклатура"}           // ссылка на объект МД
{"t":"EnumRef", "meta":"Перечисление.СтавкиНДС"}        // частный случай Ref
```

`meta` — полное имя объекта метаданных, на который ссылается тип. Если объект
не найден (например, при переносе схемы между конфигурациями), парсер сохраняет
`meta` как есть.

### Спец-типы

```jsonc
{"t":"AnyRef"}                       // ЛюбаяСсылка
{"t":"DefinedType", "name":"..."}   // ОпределяемыйТип
{"t":"Characteristic", "name":"..."} // характеристики
{"t":"Unknown", "raw":"..."}        // нераспознанный тип — сохраняется как текст
```

## 6. «Высушивание» составного типа (dry-out)

Операция редактора. Узел с `composite: true` (несколько элементов в `types`)
можно «высушить» одним из способов:

1. **Оставить подмножество типов** — пользователь снимает галки с ненужных
   элементов `types`; в файл пишутся только оставшиеся.
2. **Разнести по типам (split)** — узел дублируется по одному на каждый
   выбранный тип; имена получают суффикс (`Поле_Номенклатура`, `Поле_Контрагенты`).
   Это удобно, когда выгрузку нужно разложить на колонки определённого типа.

После высушивания до одного типа узел теряет флаг `composite`.

## 7. Формат файла данных (вторая обработка)

Контейнер тот же — NDJSON. Типы записей:

| `$`        | Описание                                                                 |
|------------|--------------------------------------------------------------------------|
| `header`   | Параметры выгрузки: схема-источник, период, отбор, режим томов          |
| `object`   | Открывает блок данных одного объекта МД: `fullName`, поля (`columns`)   |
| `row`      | Строка данных: `obj` (ссылка на `object`), `data` (объект колонка→значение) |
| `chunkEnd` | Маркер конца серверного чанка: `obj`, `count`, `cursor` (для докачки)    |
| `footer`   | Итоги: число строк, объектов, томов                                     |

Запись `header` файла данных:

```jsonc
{
  "$":"header", "format":"1cdata-ndjson", "version":1,
  "schema":"erp.1cmeta", "generated":"2026-06-15T12:00:00",
  "filters":{"dateStart":"2026-01-01","dateEnd":"2026-03-31",
             "organization":"...","subdivision":"..."},
  "split":{"mode":"objects+volumes", "maxRowsPerVolume":100000},
  "volume":1, "volumesTotal":7
}
```

### Режимы разбиения (`split.mode`)

* `single` — всё в один файл.
* `objects` — отдельный файл на каждый объект метаданных.
* `volumes` — многотомная нарезка по `maxRowsPerVolume`.
* `objects+volumes` — комбинация: для каждого объекта свой набор томов.

Имена файлов томов: `<base>.<obj>.v<NNN>.1cdata` либо `<base>.v<NNN>.1cdata`.

### Чанкинг серверных вызовов

Независимо от режима файлов, **чтение данных с сервера** всегда бьётся на
порции (`ПорцияСервера`, по умолчанию 10 000 записей) методом keyset-пагинации
(`ВЫБРАТЬ ПЕРВЫЕ N … ГДЕ Ссылка > &Курсор УПОРЯДОЧИТЬ ПО Ссылка`). Это не даёт
одному серверному вызову превысить лимиты памяти `rphost`. Маркер `chunkEnd`
несёт `cursor` — последнее обработанное значение ключа, чтобы выгрузку можно
было возобновить.
